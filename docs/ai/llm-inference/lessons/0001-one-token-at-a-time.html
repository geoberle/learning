How a model starts and continues an answer

Follow one request from input text to three pieces of generated text. By the end, you’ll be able to explain why starting an answer and continuing it involve different work.

1. Turn text into units the model can use

Large language model (LLM)
A model trained on language that can predict how text might continue. Running a trained model on new input is called inference.
Prompt
The text supplied to the model as its starting input.
Token
A unit of text represented by a number. It may be a word, part of a word, or punctuation.
Tokenizer
The component that splits text into tokens and assigns their numerical identifiers.

Our prompt is The cat. We’ll pretend it becomes two tokens. Real token boundaries and numbers depend on the tokenizer. Source: tokenizers.

2. Predict one continuation

Next-token scores
Numbers expressing how strongly the model favors each possible next token. They can be converted into probabilities.
Selection rule
The procedure that chooses one token from those predictions—for example, choosing the most likely token.

The model processes [The][ cat] and scores possible continuations. The selection rule chooses one token; in our invented example, it chooses [ sat]. That token joins the sequence. The next prediction must now continue The cat sat. Source: text generation · Selection rules.

But must the model process the entire growing sequence again each time? It can reuse some earlier work.

3. Start the answer, then reuse work

Cache
Saved computation results that can be reused. Here, it holds numerical results from processing earlier tokens.
Prefill
The stage that processes the prompt, fills the cache, and produces the prediction used to choose the first generated token.
Decode
The repeated stage that processes the latest generated token, reuses cached results, and produces the prediction used to choose the next token.

During prefill, the model processes [The][ cat]. It saves reusable results for those tokens and computes scores for what could follow [ cat], the last token of the prompt. We use those scores to select [ sat]. So prefill supplies a prediction as well as preparing the cache.

During the next decode step, the model processes [ sat] and uses the saved results for [The][ cat]. It saves new results for [ sat] and predicts what follows. We select [ down]. Earlier text still influences the prediction through the cache. Source: prefill and decode.

The prompt is already known, so prefill can process its tokens together. The continuation is not yet known: each choice supplies the input for the next decode step. This is the basic cached generation pattern; later lessons will explain exactly which results are saved.

4. Connect the phases to waiting

Time to first token (TTFT)
The elapsed time before the first generated token becomes available.
Inter-token latency
The elapsed time between successive generated tokens.

Prefill contributes to the first wait; decode contributes to subsequent gaps. The first wait can also include time spent waiting for the server to start work. Measurements have specific start and end points, so a slow first token alone does not tell you which part was slow. Source: vLLM’s timing definitions.
